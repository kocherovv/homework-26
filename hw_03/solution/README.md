## 1. Модель данных

![img.png](diagrams%2Fimg.png)
  
По схеме у меня получилось минимум 4 БД. Таблицы можно примерно распределить таким образом:  
  
```
    User DB
    ├── users
    └── couriers
    
    Restaurant DB
    ├── restaurants
    └── dishes
    
    Order DB
    ├── orders
    └── order_items
    
    Delivery DB
    └── deliveries
   
```
  
Cами таблицы приблизительно будут содержать такие колонки:  
  
```
    USERS {
        uuid id PK
        string phone UK
        string name
        string email
        timestamp created_at
    }

    COURIERS {
        uuid id PK
        uuid user_id FK
        string status
        timestamp created_at
    }

    RESTAURANTS {
        uuid id PK
        string name
        string address
        decimal latitude
        decimal longitude
        string status
        timestamp created_at
    }

    ORDERS {
        uuid id PK
        uuid user_id FK
        uuid restaurant_id FK
        string status
        decimal total_price
        string delivery_address
        timestamp created_at
    }

    ORDER_ITEMS {
        uuid id PK
        uuid order_id FK
        uuid dish_id FK
        int quantity
        decimal price
    }

    DISHES {
        uuid id PK
        uuid restaurant_id FK
        string name
        string description
        decimal price
        boolean available
    }

    DELIVERIES {
        uuid id PK
        uuid order_id FK
        uuid courier_id FK
        string status
        timestamp assigned_at
        timestamp picked_up_at
        timestamp delivered_at
    }
```

## 3. Шардирование

При большом кол-ве пользователей может потребоваться горизонтальное масштабирование реляционных БД пользователей, заказов и доставок.
Ключом шардирования будут user_id, id заказа, id доставки соответственно. Redis для шардирования использует идентификаторы ключей, а монга при необходимости может шардироваться по id ресторана, но это вряд-ли понадобится.
Нам важно чтобы данные одного ресторана/пользователя/ доставки были в одной ноде/чанке, чтобы избежать запросов агрегирующих запросов и в случае потери шардов страдали данные минимального кол-ва пользователей/рестаранов/заказов, хотя это и может привести к не много неравномерному распределению данных.

## 4. Кэширование

Скорее всего кеширования на уровне БД будет достаточно. Создание заказов и доставок не сверхвысокочастотные запросы и довольно уникальные, поэтому частый запрос одних и тех же данных не ожидается.
Монгу с меню вероятно придется кешировать на уровне restaurant service в Redis, простым Read-Through.

| Что кэшируем     | Уровень | Стратегия | TTL | Инвалидация | Зачем (выигрыш) |
|------------------|---|---|---|---|---|
| _меню ресторана_ | _Redis_ | _Read-Through_ | _5 мин_ | _по событию update_ | _снять нагрузку с БД на чтении_ |
| …                | | | | | |

## 6. CAP trade-offs

_Как решение соотносится с CAP-теоремой._
Благодаря сетевому балансировщику на входе и наличию очередей перед всеми нагруженными сервисами, а так же тому, что сервисы эти stateless и при наличии нескольких инстансов могут распределять нагрузку, я думаю удалось изобразить универсальную схему.
Все используемые БД поддерживают и репликацию и шардирование, поэтому при необходимости можно быстро маневрировать под потребности сервиса.
Если нужна высокая доступность настроить кластер с репликами для любой из БД или брокера и наоборот.

Для текущей системы вероятно потребуется Hot Standby репликация PostgreSQL пользователей, заказов и доставок так как потеря данных с БД с оплаченными заказами и юзерами очень критична.
Согласованность данных не должна при это сильно пострадать, так как клиент получает информацию о заказе из уведомлений, а состав заказа не меняется после создания.
Для базы ресторана как минимум бекапы настроить - Cold Standby, там нам важна согласованность данных, чтобы ассортимент и цены были актуальны.
