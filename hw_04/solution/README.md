# ДЗ 4. Сайзинг, стоимость и оптимизация — решение

> Условие: [../Задание.md](../Задание.md). Схемы и расчёты — в [diagrams/](diagrams/).
> Методика и юнит-цены — из раздаточного справочника занятия (конвейер расчёта, инженерные константы, unit-цены).

> Выполняется для системы, выбранной в ДЗ 2/ДЗ3 (доставка еды).

## Допущения

Официальные вводные (ДЗ4): MAU 5 000 000, DAU 500 000, 2 заказа/пользователя в неделю, пик ×3.

Что добавлено сверху (явно, чтобы можно было оспорить):

- Нагрузка считается от DAU, не MAU — по методичке: «расчёт нагрузки почти всегда ведут от DAU». MAU — размер аудитории, не нагрузка в моменте.
- Частота: 2 заказа/неделю → 2/7 ≈ 0.286 заказа на DAU в день.
- Fan-out каталога: 1.5 открытия приложения на DAU в день, 6 запросов на открытие (список + ~4 карточки ресторана + 1 открытие меню).
- Статус заказа: 3 обращения к экрану заказа на 1 заказ; дальше статусы идут push через SSE.
- Курьеры: не гадаем количество, а выводим через Little's Law (L = λ×W) из объёма заказов. Апдейт локации — раз в 5 сек.
- Рестораны/блюда: 100 000/50.
- Фото: 1 фото/карточку, ~150 КБ сжатое, CDN cache-hit 90% (нижняя граница справочника).
- Средний JSON-ответ: 2 КБ (в диапазоне 1–5 КБ).
- Накладные БД: ×2.5 (середина диапазона ×2–3 из справочника).
- Рост DAU за 3 года условием не задан — считаем DAU фиксированным.

## 1. Расчёт RPS

### Сценарии → запросы в сутки

```
Заказы/сутки = DAU × (2 / 7) = 500 000 × 0.2857 ≈ 142 857

Открытий приложения/сутки = DAU × 1.5 = 750 000
Запросов каталога/меню в сутки = 750 000 × 6 (fan-out) = 4 500 000

Просмотров статуса заказа/сутки = Заказы/сутки × 3 = 428 571
```

### RPS — запись

```
Создание заказа + оплата (один поток, тот же Saga-шаг):
  avg RPS = 142 857 / 86 400 ≈ 1.65
  peak RPS = 1.65 × 3 ≈ 5

Локация курьеров — через Little's Law:
  L (одновременно "в доставке") = peak RPS(заказов) × среднее время доставки
                                 = 5 × 2100 сек (35 мин) = 10 500 активных доставок
  RPS апдейтов = 10 500 / 5 сек ≈ 2 100 
```

### RPS — чтение

```
Каталог/меню:  avg = 4 500 000 / 86 400 ≈ 52.1   peak = 52.1 × 3 ≈ 156
Статус заказа: avg =   428 571 / 86 400 ≈ 4.96   peak =  4.96 × 3 ≈ 15
```

| Поток | Тип | avg RPS | peak RPS |
|---|---|---|---|
| Создание заказа + оплата | запись | ~1.65 | ~5 |
| Локация курьеров | запись | ~700 | ~2 100 |
| Каталог/меню | чтение | ~52 | ~156 |
| Статус заказа | чтение | ~5 | ~15 |

Локация курьеров на два порядка больше остального

## 2. Расчёт хранилища

### Order DB (PostgreSQL) — растёт со временем

```
Байт на заказ (сырые, из модели ДЗ3):
  orders ~190 + order_items(×3) ~345 + deliveries ~128 + payments ~120 ≈ 783 байт

С накладными БД (×2.5): 783 × 2.5 ≈ 1 958 байт ≈ ~2 КБ/заказ

Год 1: 142 857 × 365 × 2 КБ ≈ 104 285 610 КБ ≈ 104 ГБ
Год 3 (DAU фиксирован): 104 × 3 ≈ 313 ГБ
```

### Restaurant DB (MongoDB) — почти не растёт со временем

Из ДЗ3: ~2.4 ГБ при 100 000 ресторанов × 50 блюд. Растёт с числом ресторанов, не со временем — темп роста каталога условием не задан, оставляем плоским.

### Фото (объектное хранилище)

```
100 000 ресторанов × 50 блюд × 1 фото × 150 КБ ≈ 750 000 000 КБ ≈ 750 ГБ
```

| Хранилище | Год 1 | Год 3 | Тип |
|---|---|---|---|
| Order DB | ~104 ГБ | ~313 ГБ | Блочный SSD |
| Restaurant DB | ~2.4 ГБ | ~2.4 ГБ | Блочный SSD (малый) |
| Фото ресторанов/блюд | ~750 ГБ | ~750 ГБ* | Объектное (hot/cold) |

\* без учёта роста каталога — условие не даёт темп роста, отмечено как допущение.

## 3. Расчёт bandwidth

### JSON (не медиа)

```
Запросов чтения/сутки = 4 500 000 + 428 571 ≈ 4 928 571
Egress/сутки = 4 928 571 × 2 КБ ≈ 9.6 ГБ
Egress/месяц = 9.6 × 30 ≈ 288 ГБ
```

### Фото

```
Фото/сутки = 750 000 открытий × 8 фото ≈ 6 000 000
Egress/сутки = 6 000 000 × 150 КБ = 900 ГБ
Egress/месяц = 900 × 30 = 27 000 ГБ = 27 ТБ

Пиковая полоса:
  peak фото/сек = (6 000 000 / 86 400) × 3 ≈ 208
  peak bandwidth = 208 × 150 КБ ≈ 31 250 КБ/с ≈ 250 Мбит/с ≈ 0.25 Гбит/с
```

| Поток | В месяц | Пиковая полоса |
|---|---|---|
| JSON API | ~290 ГБ | незначительна |
| Фото (origin, без CDN) | ~27 ТБ | ~0.25 Гбит/с |

Фото — на два порядка больше JSON по объёму. Ключевая статья network.

## 5. Расчёт стоимости

### Compute

```
2 + 2 + 14 = 18 инстансов × $120/мес ≈ $2 160/мес
```

### Storage (объектное, фото)

```
Hot (20%): 150 ГБ × $23/ТБ-мес ≈ $3.5
Cold (80%): 600 ГБ × $4/ТБ-мес ≈ $2.4
Итого ≈ $6/мес
```
(Блочное хранилище БД уже внутри Managed — справочник: managed-цена включает compute+диск.)

### Network

```
Прямая раздача (без CDN):
  Фото: 27 000 ГБ × $0.08 = $2 160
  JSON: 288 ГБ × $0.08 = $23
  Итого напрямую ≈ $2 183/мес

Через CDN (95% фото уходит в CDN):
  origin: 27 000×5% = 1 350 ГБ × $0.08 = $108
  CDN:    27 000×95% = 25 650 ГБ × $0.02 = $513
  + JSON напрямую: $23
  Итого с CDN ≈ $644/мес
```

### Managed (БД, кэш, очередь, LB)

```
Order DB:      2 × $240 self-host-экв. × 2 (managed) ≈ $960
Restaurant DB: 3 × $120 × 2                            ≈ $720
Redis:         3 × $120 × 2                            ≈ $720
Kafka:         3 × $120 × 2                             ≈ $720
LB: $25 + 27 300 ГБ × $0.008                            ≈ $243
Итого managed ≈ $3 363/мес
```

### Итоговая раскладка (с CDN)

| Ось       | $/мес      | Доля     |
|-----------|------------|----------|
| Compute   | ~2 160     | 35%      |
| Storage   | ~6         | 0.1%     |
| Network   | ~644       | 10%      |
| Managed   | ~3 363     | 54%      |
| Итого | ~6 173 | 100% |

```
Cost/DAU = 6 173 / 500 000 ≈ $0.012/мес
```

Проверка на здравый смысл: при среднем чеке ~$15 и комиссии платформы ~15%, выручка с одного DAU ≈ 0.286 заказа × $15 × 15% ≈ $0.64/день ≈ $19/мес — инфраструктура (~$0.012/DAU) это доли процента от выручки на пользователя, экономика сходится с большим запасом.

## 6. Оптимизация

### Узкое место

Managed (54% счёта) — но не из-за нагрузки: Postgres, Mongo, Redis и Kafka по отдельности несут скромный объём данных/RPS (разделы 1–2). Счёт раздувает количество отдельных managed-кластеров, каждый из которых держит минимальную HA-топологию (2–3 ноды) вне зависимости от того, насколько мало он нагружен. При росте нагрузки в 10 раз managed вырастет слабо (топология по минимуму останется той же), а вот network (фото) и compute будут расти почти линейно с DAU — именно они станут узким местом на бо́льшем масштабе, не managed.

### Три оптимизации

| # | Что делаем | Экономия | Чем платим |
|---|---|---|---|
| 1 | CDN для фото вместо прямой раздачи с origin | −$1 539/мес (~20% от базового счёта без CDN: $7 712 → $6 173) | Инвалидация кэша при смене фото ресторана, доп. интеграция |
| 2 | Redis для локации — 1 инстанс без кластера вместо 3-нодового (данные допускают короткую потерю по AOF, обосновано в ДЗ3) | −$480/мес (~8% от итога) | Нет автоматического failover: при падении единственной ноды сервис локации недоступен до restart. Риск принят — геоданные не критичны и быстро "протухают" сами, доставка идёт и без live-трекинга |
| 3 | Reserved instances (1 год) на стабильную часть compute-парка (без ×2 буфера под пик/отказ — он должен оставаться эластичным) | −$540/мес (~9% от итога) | Коммит на год, меньше гибкости при падении нагрузки |

```
Итого после оптимизации ≈ 6 173 − 480 − 540 ≈ $5 153/мес
(против $7 712/мес "наивной" раскладки без CDN и без right-sizing Redis — экономия ~33%)
```

Что выглядит разумной оптимизацией, но здесь бессмысленно: сокращение Kafka до 1–2 брокеров. В ДЗ3 семантика доставки зафиксирована как `acks=all`, `min.insync.replicas=2` — это требует минимум 3 брокера для настоящей отказоустойчивости. Сокращение ниже прямо противоречит уже принятому в ДЗ3 CP-решению по Kafka, а экономия на этой статье (~$480/мес управляемого Kafka) невелика относительно риска потери сообщений.
